# 部屋単位の監査と、似た物件の中での順位付け(08〜11)

ChatGPTが作った原案を、実データで動かして直したもの。既存の `01〜07` と `src/` の他のファイルは変更していない。

## 何をするか

| ファイル | 内容 |
|---|---|
| `src/listing_episodes.py` | 建物ID＋住戸IDで同じ部屋の重複・連続掲載を統合する。矛盾の判定は、つなごうとしている掲載どうしだけで行う。最寄駅の違いは記録のみで統合は止めない |
| `analysis/08_unit_audit.py` | IDの有無、統合できた件数、統合できなかった理由(間取り・面積の食い違い)を出す。統合ルール0/1/7/14日の感度つき |
| `analysis/09_candidate_ranking.py` | 同時に掲載中の似た物件(間取り×築年数10年帯×家賃2万円帯)の中で、7方式の順位付けを比べる。グループ単位のブートストラップで95%区間を出す。`--gap N` で統合ルールを選ぶ |
| `analysis/09b_segment_sensitivity.py` | 候補集合の「似かた」を5通りに変えて、属性が順位付けに足す情報を測る(探索的) |
| `analysis/11_two_level_priority.py` | 優先度の境界(2022年の重み付き3分位点)を決め、2023年に固定して実終了率を出す。報告書の35.71% / 51.66%と17.2・17.3節の表を再現する |
| `tests/test_listing_episodes.py` | 統合ロジックの単体テスト(5件) |

`summary_tables/` に、2026-10-12に実行した結果の要約表を入れている(生成物の`results/`はgitignoreされている)。

## 実行順(Ohoriフォルダから)

```
python -m pip install -r requirements.txt
python -m unittest discover -s tests -p test_listing_episodes.py -v
python -m analysis.08_unit_audit
python -m analysis.09_candidate_ranking --gap 1
python -m analysis.09b_segment_sensitivity
# 11は 04, 06, 07 を先に実行しておく
python -m analysis.11_two_level_priority
```

入力は、リポジトリ直下の `data/prepared/kokubunji_raw.parquet`(`src/data.py` の `SOURCE_COLUMNS` で国分寺市を抽出したもの)。

## 結果の要点(2020〜2023年・国分寺市)

- 全掲載にIDがある。統合すると、2020〜2023年の掲載は22,332件から15,276件になる(ルール1日)。間取りや面積が食い違う779組(6,415掲載)は統合していない。
- **似た物件の中の順位付けは、どの方法もAUC約0.53〜0.55。** Model 2は、掲載経過日数だけを使う方法と差がない(差−0.004、95%区間は−0.038〜+0.016)。統合ルールを変えても同じ。
- 候補の種類が違うほど属性が効く。間取りだけが同じなら+0.026、条件なしなら+0.044(`09b`)。
- 報告書の15〜17節の数字(Brier、AUC、境界値、優先度ごとの実終了率)は、すべて再現できた。

## 注意

1. `building_id`＋`unit_id`が同じでも、実際に同じ部屋とは断定していない。間取りの食い違いが603組あり、IDが部屋を一意に表さない場合がある。
2. 統合ルール(重なる掲載、1日以内の連続)は仮定で、0/1/7/14日の感度を見る。
3. 掲載終了は成約ではない。
4. 2023年の結果を見たあとの追加分析なので、独立した未使用のテストではない。
5. `09`の学習は、2023-01-01より前に分かる掲載終了情報だけを使う。報告書の数値と一致しない場合がある。
6. 大きい候補集合(`09b`)は、同じ物件が複数の日に出るため区間を出していない。
7. `11`の「高/低」は、予測リスクを中央値で分けたもの。掲載期間の長短で分ける方式とは別物。
